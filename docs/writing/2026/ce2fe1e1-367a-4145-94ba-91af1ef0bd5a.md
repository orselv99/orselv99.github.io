## 서빙 프레임워크 선택
집 컴퓨터 스펙은 RTX 4060 Ti 8GB 라서 선택의 폭이 좁다. 집에서는 주로 Ollama 에 양자화된 가벼운 모델들을 돌려보거나, ComfyUI 에 Diffusion 모델을 물려서 이미지 뽑는 용도로 쏠쏠하게 써왔다. 회사 머신 스펙은 NVIDIA RTX 6000 Ada 48GB 로 테스트용으로 나쁘지 않았다. 익숙한 Ollama 로 빠르게 할까 했는데 서버 스펙도 넉넉해서 요즘 현업에서 다들 쓴다는 vLLM 을 공부해보고자 선택하게 됬다.

<br/>

## Ollama 와 vLLM 뭐가 다를까?

### 1. Ollama

![alt text](./ce2fe1e1-367a-4145-94ba-91af1ef0bd5a-1.png)

Ollama 는 사용법이 매우 쉽다. 로컬환경에서 사용하기 좋은 <span style="color: var(--color-accent-impl);">GGUF 양자화 모델을 서빙하여 빠르게 테스트할 때 압도적으로 편하다.</span> 대용량 트래픽을 처리하기보다는 기본적으로 한두 명의 요청을 처리하는 데 최적화되어 있다. <span style="color: var(--color-accent-spec);">여러 사용자가 동시에 요청하게 되면 대기열이 생기고(정적 배치), 문맥(Context)이 길어지면 메모리 단편화가 생겨 VRAM 낭비가 생긴다.</span>

### 2. vLLM

![alt text](./ce2fe1e1-367a-4145-94ba-91af1ef0bd5a-0.svg)

여러 명의 동시 요청을 쳐내는 처리량에 장점을 갖는 엔진이라고 한다. 

- OS 의 가상 메모리 페이징처럼 KV Cache 를 쪼개서 관리하는 `PagedAttention` 기술 덕분에 메모리 낭비가 거의 없다
- 요청이 들어오는대로 유연하게 묶어서 처리하는 Continuous Batching(연속 배치) 덕분에 트래픽이 몰려도 처리 속도가 좋다
- Prometheus 메트릭 엔드포인트(/metrics) 를 기본 지원해서 모니터링 붙이기 좋다

하지만, 당연히 이런 뛰어난 기능 뒤에는 매우 복잡한 초기 설정이 기다리고 있었다. 모델별 VRAM 비율(--gpu-memory-utilization) 이나 토큰 길이, 배치 파라미터를 엔지니어가 직접 세심하게 조율해야했다.

## 모니터링 세팅
Prometheus 메트릭을 기본 지원한다고 해서 리소스를 시각화 해보기로 했다. 배포 파일들을 코드로 관리(Provisioning) 할 수 있도록 Prometheus 와 Grafana 환경을 구성했다.

[Presidio](https://github.com/data-privacy-stack/presidio) 는 CPU 로 초기화하여 사용해도 충분한 경량 라이브러리라서 제외

|모델|비율|할당 VRAM|
|---|---|---|
|[RedHatAI/gemma-4-12B-it-FP8-Dynamic](https://huggingface.co/RedHatAI/gemma-4-12B-it-FP8-Dynamic)|0.75|36GB|
|[Kanana Safeguard-Prompt-2.1B](https://huggingface.co/kakaocorp/kanana-safeguard-prompt-2.1b)|0.15|7.2GB|
|CUDA 컨텍스트 및 시스템 버퍼 (GPU Headroom)|0.10|4.8GB|

차후에 `Kanana Safeguard-Prompt-2.1B` 를 내리면서 LLM 에 0.9 를 할당해서 사용하게 됬다.
